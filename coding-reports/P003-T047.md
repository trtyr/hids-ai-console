四轮各干什么（同一份会话里，`turns[].phase`）：

1. `case`：读案卷 `01-原始告警.txt` / `03-研判事实.md` / `result.json`（结论、命中规则 id、引用过的判据页）；
2. `libraries`：读两库——规则库清单 + 命中规则的 Rego 原文；知识库目标页正文与同场景其他页；
3. `propose`：**一次**模型调用决定「动哪几边、为什么」（域 `false_positive`、role `fp_maintainer`）；没配决策模型或回包解不出来 →
   `decision.source='fallback'`，按请求的库逐个尝试（决策来源如实记在会话与 `maintenance.decision` 里）；
4. `verify`：写入 + 自校验（规则读回 revision、旧版是否进了 `rules-history`、知识库会话是否已终态），然后定终态 `done` / `partial` / `failed`。

- 单腿补跑时没请求的那一侧记 `status:'updated'` + `state:'skipped'` + `why:'本次只补跑 …：… 侧未执行'`——不谎报「改完了」，也不把总态钉在 `updating`。

3. **规则侧幂等版本按「案件命中的规则」算**：命中为空时退化成整库摘要。极端情形——维护者新增了一条规则、而案件 result.json 里
   没有这条 id——补跑时版本仍取整库（若命中为空）或只取旧命中集（若命中非空），可能把「新增的那条已经在了」判成同版本跳过。
   语义上仍是「这一案件相关的规则没变，不重复跑」，但要让新增规则也进幂等口径，得把「本轮写过的规则 id」累加进案件的维护侧。
4. **重启残留不自动恢复**照旧（P003-T013 报告已记）：进程死在维护中途，记录停在 `updating`，不挡重新登记（`runningMaintenance` 只在内存），
   重新登记会开一份新会话——不会自动接着那份旧的。
5. **注入替身缺读接口时自校验降级**：`wiki.get` / `recordPublished` 不存在时对应 `checks` 项标 `skipped:true`，不当失败。生产实现都有这两件，
   单测/探针的替身不该因此把整轮判失败——处理与申报见 `fp-maintainer.js` 的 `#page()` / `#maintainWiki()` / `maintain()`。
6. **`fs.rename` 覆盖目标的那一步**（`FpSessionStore.save()`）是进程内原子：同目录多进程同时写同一个会话 id 不在本卡处理范围
   （会话 id 是每轮新 UUID，实际不会撞；这条只是把「原子」的边界说清）。
