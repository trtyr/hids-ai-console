## 三、文档里每条断言的出处

架构篇共 **263 处** `文件:行号` 引用（涉及 325 个具体行号），已知边界篇另有 19 处。全部逐条机器核对过：文件存在、行号在文件范围内。核对脚本：

```bash
node -e '
const fs=require("fs");
for (const file of ["docs/architecture.md","docs/index.md","docs/_meta/gaps.md"]) {
  const text=fs.readFileSync(file,"utf8");
  const re=/([A-Za-z0-9_.\/-]+\.(?:js|yaml|json|md))[`?:]*:(\d+)(?:-(\d+))?/g;
  let m,refs=0,bad=0;
  while((m=re.exec(text))){
    const f=m[1]; refs++;
    if(!fs.existsSync(f)){bad++;continue;}
    const fl=fs.readFileSync(f,"utf8").split("\n").length;
    const a=+m[2],b=m[3]?+m[3]:a;
    if(a<1||b>fl) bad++;
  }
  console.log(file,"引用处数:",refs,"问题:",bad);
}
'
```

## 四、关键发现

1. **运行态数据落在仓库外**。`server.js:24` 把运行态根目录定为「本文件所在目录的上一级」，数据落在 `<上一级>/backend/.data/`；本仓目录名是 `hids-ai-console`，所以数据实际在 `/home/trtyr/.pi-worktrees/hids-ai-console/hids-ai-console/backend/.data/`。同一约定写在 `maintenance-startup.test.js:12-14`，当前目录名下它是 `node --test` 里唯一的失败项。
2. **`node --test` 实测 99 项，98 过 1 挂**。失败项就是上面那条，错误为 `Cannot find module '.../current/backend/maintenance-server.js'`。跑测试前后 `git status --short` 只有新增的 `docs/`，没有改动任何既有文件。
3. **业务 API 冒烟实跑过**（`HIDS_PORT=18099 node server.js`，本机 8080 被别的进程占）：不配凭据时，读本地状态的接口（`/api/session`、`/api/status`、`/api/agent/status`、`/api/updates`、`/api/agent/prompts`、`/api/triage/rules`、`/api/wiki/pages`）返回 200；需要牧云或模型的（`/api/alerts`、`/api/agent/triage/status`）返回 503 并写明缺什么。完整输出见 `evidence/recon/P001-T001.md` 第六之二节。验证完已 kill 进程。
4. **候选经验整理台未接线**。`knowledge-store.js` / `knowledge-workbench.js` 只被两个测试文件 import，业务进程加载的是 `wiki-store.js` / `wiki-workbench.js` 那套。
5. **`createServer` 有两个参数没有使用点**：`maintenanceEntry`（`server.js:115`）与 `knowledge`（`server.js:112`）。

这四条都已写进 `docs/_meta/gaps.md`，并在架构篇第 8.1、4、13 节给出对应上下文。

## 五、未决

下面五条是本卡**没有解决**的问题，写在这里以免被当成已交付。

1. **`docs/modules/` 下的 14 个模块页还不存在。** `_breakdown.json` 的 `doc` 字段指向这 14 个待建页面（`docs/modules/<name>.md`），它们由模块卡逐篇写。本卡 scope 只含 `_breakdown.json` 这个清单文件，不含模块页正文，所以本卡无法把它们建出来。清单里的 `files` 字段已逐个验证存在；`doc` 字段是下游模块卡的落点，不是现存文件。
2. **牧云侧的真实响应格式没验证。** 本机没有牧云凭据，本卡未发起任何外部请求。架构篇里关于牧云字段的一切描述，依据的是代码中的映射表（`cloudwalker.js:16-74`、`evidence-view.js:4-47`），不是实测响应。若实际响应与映射表不符，相关段落要跟着改。
3. **模型的实际行为没验证。** 没有真实模型服务，文档只写代码如何约束模型输出，不描述模型表现。
4. **两套「知识库」并存的原因没查到。** 代码、注释、`git log` 里都没有说明 `knowledge-*` 与 `wiki-*` 是新旧替代还是并存设计。这一条需要问产品或开发，代码里找不到答案。
5. **`openapi.yaml` 与 `server.js` 未逐条比对。** 契约文件声明有 35 条路径，本卡核对了条数与两处引用，没有逐条比对参数与响应体——那是接口契约卡的事。若那边发现不一致，架构篇第 11.3 节提到「两套真源」的说法要跟着调整。

另外，「未决」还包括一条已确认但本卡不改的事实：`docs/architecture.md` 里的行号对应写文档时的基线提交 `a16e0d5`（文档本身由本分支上的 `320ebbc` 与 `e4daac0` 两个提交引入）。代码一旦改动，这些行号要重新核一遍。
