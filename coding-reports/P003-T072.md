## 1. 设计（acceptance 第 1 条：字段规范 / 分级 / 采样与保留 / 容量估算）

- **通用上下文**：每行恒有 `time / level / event`；处于请求上下文时自动带 `request_id`（与已登录的 `user`）。既有键名只增不改。
- **请求链**：`http.request` 行 = `method / path / status / duration_ms / user`（无登录态 user 写 null，不省键）+ ALS 注入的 `request_id`。同一请求的全部日志（含 `config.updated`、`data.cleaned`、`ai.model_call`…）共享同一 `request_id`。
- **错误链**：`http.failed` 带 `status / error`（原文只进日志不外发）；配合 R-ERROR，响应里的 code + 日志里的 request_id 构成「code 给程序、request_id 给人」的闭环。
- **分级**：info / warn / error 三级不变（`queryLevels`）。
- **采样与保留**：不做采样（私有部署量级不需要）；保留 = 单文件 10 MiB 轮转 + 历史留 5 份 + **总量上限 200 MiB**（`HIDS_LOG_TOTAL_MAX_BYTES`，超限从最老的历史文件删起，当前文件永不删）。
- **容量估算**：单行约 200–400 B；按日均 2 万请求（每请求 2–5 行）≈ 20–50 MB/日；10 MiB×5 份 ≈ 50 MB 滚动窗口，200 MiB 总量上限 ≈ 4–10 天历史，超限自动收敛，不会写满盘。

1. **设计先行** ✅（本节）。
2. **默认落盘** ✅：不配任何变量 → `<数据根>/logs/hids.log`（T034 的部署树用例已把 `logs/hids.log` 列入「进程自己写的运行态」白名单）；`HIDS_LOG_FILE` 仍可覆盖；显式关闭 = `HIDS_LOG_FILE=none|off`。测试进程（`NODE_TEST_CONTEXT`）默认关，不污染真实数据根；单测注入 `{test:false}` 可验默认路径（A1 + log-system 均有）。
3. **request_id 贯穿** ✅：ALS（`runWithRequestContext`）——业务端与维护端每个请求一个上下文，身份认证后回填 `user`。反查示例：`GET /api/logs?request_id=req-1` 一次取回该请求的 `http.request` + `config.updated` 全链（log-system.test.js 第 2 条即此实操）。
4. **日志行带 user / route / method / status / duration_ms** ✅（无登录态写 null）。

7. **轮转与保留三重上限** ✅（单文件 / 份数 / 总量；超限删最老历史、不丢当前行；零丢失实测：50k 行连发 keep=100 全部落盘）。

## 3. 排查记录（本卡最重的发现，已修复）

全量套件下 T047 的 A5（`ai.model_call` 事件绝对条数）稳定失败而单跑通过。轮转探针（临时，已删）抓到现场：**轮转在 3KB 时触发**——根因是批量 drain 里 `await appendFileAsync` 让出事件循环期间新写入队列，恢复后 `if (queue.length) rotate()` 把「并发到达的新行」误判成轮转边界，**每次并发写都触发一次假轮转**，事件散进轮转历史文件，只读当前文件的用例就少了。修复：显式 `hitBoundary` 标记，只有真撞单文件上限才轮转。修复后全量 evidence 复跑验证。这个 bug 同时解释了并发 100 压测早期的吞吐塌陷（renameSync 风暴）。
