## 四、关键发现

1. **证据编号先分配、后调用**。`EvidenceSession.callTool` 在调工具之前就 `++this.started` 并定下证据编号（`agent-tools.js:59-60`），记录则在调用成功后才写入 `records`（`agent-tools.js:66`）。所以**失败的调用会占掉一次取证名额，却不留记录**。实测（`maxCalls=2`）：失败一次后 `started = 1`、`records = 0`，第三次调用报「本次调查的取证调用已达到 2 次上限」。
2. **主机事件的 `total` 只算成功类型**。失败类型的数量不在 `total` 里，得连着 `errors` 与 `partial` 一起读（`api-tools.js:55`、`api-tools.js:61`）。实测部分失败时返回 `partial: true`、`errors: {"honeypot": "蜜罐接口超时"}`，`total` 只含成功类型之和。
3. **`types` 长度检查在去重之前**。11 的上限按原始数组算（`api-tools.js:46`），去重发生在之后（`api-tools.js:50`）。实测 11 个重复项过了长度关，实际只查 1 类。
4. **两处 2,000,000 上限量的是不同的东西**。MCP 侧量工具返回文本的字符数（`mcp-client.js:72`），会话侧量 `{name, args, result}` 序列化后的长度（`agent-tools.js:61-62`）。
5. **常规研判每次调用都重拉一次 API 工具清单**（`agent-tools.js:108`），没有像深度研判那样的 `catalog` 缓存（`agent-tools.js:34`）。
6. **白名单 47 个名字、无重复**（实测）；其中只有 8 个命中常规研判那条正则，常规研判合并后的工具数是 31（23 + 8）。
7. **架构篇第 5.1 节写的是「约 40 个名字」，实测是 47**（`docs/architecture.md:122`）。本页按实测写 47，架构篇那份数字偏小。`docs/architecture.md` 不在本卡 scope，本卡没有改它；这一条 P001-T001 的审查已经报告给群主。
