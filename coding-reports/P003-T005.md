## 二、本卡定下的对外契约（测试照这个写）

### A1 `GET|PUT /api/wiki/pages/{pagePath}`：404 只给相对路径

| 情形 | 状态码 | 正文 | 判据 |
| --- | --- | --- | --- |
| 路径语法合法、文件不存在 | 404 | `{"error":"知识库页面不存在：<相对路径>"}` | `wiki-store.js:75-83` |
| 路径语法非法（目录不在白名单、文件名不合规） | 400 | `{"error":"知识库页面路径无效"}` | `wiki-store.js:32-39`（未变） |
| 页面存在 | 200 | 页面对象（`content` 等，未变） | `wiki-store.js:82` |

- **承诺**：404 正文**不含**服务器绝对路径（不含 wiki 目录、不含 `/home/`）。GET 与 PUT 同一口径（PUT 内部经 `get()`，`wiki-store.js:162`）。
- **可断言**：正文严格等于 `{"error":"知识库页面不存在：common/GEN-99.md"}`；且 `!body.includes(<wiki 目录>)`。
- 页面不存在时写接口的响应**优先级**：先校验 `expected_revision`（400 缺版本），再 404。

### A2 `GET /api/agent/triage/status`：syslog 模式新增 `syslog` 对象

`input_mode === 'syslog'` 时 200 正文多一个键（其余键不变）：

```json
{"initialized":true,"enabled":true,"input_mode":"syslog","last_poll_at":null,"last_error":null,
 "counts":{"queued":0,"running":0,"done":0,"failed":0},
 "syslog":{"listening":false,"bind":null,"error":"bind EADDRINUSE 127.0.0.1:15599"}}
```

| 字段 | 类型 | 语义 |
| --- | --- | --- |
| `syslog.listening` | boolean | 进程是否真的绑上了 UDP 端口；`false` = 这条 syslog 输入一条消息也收不到 |
| `syslog.bind` | string \| null | 绑上时的 `udp://<address>:<port>` |
| `syslog.error` | string \| null | 绑定失败的原因（截 300 字），如 `bind EADDRINUSE 127.0.0.1:15514` |

- 三态可区分：**未尝试绑定** `{listening:false, bind:null, error:null}` / **绑上** `{true, "udp://…", null}` / **绑定失败** `{false, null, "<原因>"}`。
- `input_mode === 'poll'` 时**不出现** `syslog` 键，仍出 `interval_ms`（形状与改动前一致）。
- 绑定失败**不影响** HTTP 服务与队列：`enabled`、`counts` 照常。

### A5 `POST /api/triage/rules/validate`：400 文案分两种

| 请求正文 | 状态码 | `error` |
| --- | --- | --- |
| 不是 JSON | 400 | `请求正文不是 JSON` |
| 超过 100000 字 | 400 | `请求正文过大` |
| `null` / 数组 / 字符串 / 数字 / 对象但无 `config` 键 | 400 | `请求正文缺少 config` |
| 有 `config` 键但值不是合法规则集（`null`、数组、`rules` 非数组、字段越界…） | 400 | `规则集格式无效`（或 `triage-rules.js` 的具体校验文案） |
| 合法规则集 | 200 | `{"valid":true,"count":<rules.length>}` |

- **承诺**：任何请求都不会把 `Cannot read properties of null` 这类英文内部 TypeError 文案回给调用方。
- `count` 是**校验通过的那份 config** 的 `rules.length`。

## 三、A3（B21）：`/api/status` 的 502 契约 —— 本卡不改代码，交 T004 落 openapi

群主口径：保持 502 不变，契约写在这里交给 T004。实现现状 `server.js:210-215`：

| 情形 | 状态码 | 正文 |
| --- | --- | --- |
| 未配置牧云（无 `CLOUDWALKER_URL` / `CLOUDWALKER_API_TOKEN`） | 200 | `{"configured":false,"connected":false,"reason":"请设置牧云地址和 API Token"}` |
| 配置了且连通 | 200 | `{"configured":true, ...service.status()}` |
| 配置了但连不上牧云（`service.status()` 抛错） | **502** | `{"configured":true,"connected":false,"reason":"<上游错误原文>"}` |

- **502 的语义**：不是「服务整体不可用」，而是「配置在、牧云连不上」。所以 `/api/status` **不走 503**，正文仍带完整状态三字段。
- 客户前端 `web/src/status.js:47` 用 `acceptStatus: [200, 502]` 接，两码都按 `normalizeCloud` 解析（`web/src/status.js:90-96`）。
- **T004 要落的 openapi 段落**：`openapi.yaml:42-70`（`/api/status` 的 `200` / `502` 两个 response）——现状已描述 502 正文，需补两点：① 502 只表示牧云连接失败，未配置走 200；② `reason` 是上游错误原文，不做脱敏承诺。本卡新增的 `syslog` 字段也要 T004 进 `TriageSummary`（`openapi.yaml` 里 `TriageSummary` 的 `input_mode` 附近）。
- 本卡的 pin 测试：`error-observability.test.js` 的 `/api/status 连不上牧云是 502…`（断言 502 + 三字段 + `content-type: application/json; charset=utf-8`，另断言未配置分支 200），改坏状态码会红。
