## 二、验收逐条

### A1 有误报入口，带理由。这一条的结论立刻成为误报，不等维护者跑完

- 入口：`POST /api/agent/triage/{alertId}/false-positive`，正文 `{reason, who?}`（`server.js:597-632`）。
  理由必填 10 到 4000 字，登记人至少 2 字（省略取业务账号名，未启用 Basic 认证时是 `operator`）。
- 顺序：`record.verdict = 'false_positive'` → `feedback{reason,who,recorded_at}` → `await monitor.persist?.()`（`server.js:618-624`）
  → 才 `json(res, 202, ...)`；两个维护者在 `server.js:626` 才起，响应不等它们。
- 单测 `agent-api.test.js:522` 把两个维护者都卡在未决 Promise 上：POST 回 202 后立刻断言
  `body.verdict.verdict === 'false_positive'`、`body.maintenance.status === 'updating'`、`monitor.persisted >= 1`，
  再 `GET /api/agent/triage/{alertId}`（走真的 `monitor.status()` 口径）读到的同样是误报 + `updating`。
- 入参单测 `agent-api.test.js:574`：缺理由 / 理由 3 字 / 登记人 1 字 → 400；不存在的案件 → 404；`bad-id` → 400；
  `status: 'running'` 的记录 → 409「研判还没结束，不能登记误报」，且原记录的 `verdict`、`feedback` 未被改动。

### A2 规则维护者改的是 Rego，加一条或改一条，不重写整本

- `RegoRuleMaintainer.maintain`（`server.js:145-177`）：模型输出一条 Rego（JSON `{ready,id,name,reason,rego}`），
  `ready:false` / id 不合法 / 正文为空都直接抛错（`failed`，不落盘）。
- 写盘前校验：`mkdtemp` 临时目录 + 真 `RuleStore(目录).read(id)`（`server.js:120-128`）——只认规则子集，语法出子集即抛错带
  `rules/<文件>:<行>`；写盘后再 `new RuleStore(目录).list()`（`server.js:131-138`）确认整库仍可装载（拦重复 id）。
- 只碰一个文件：目标文件名取 `existing?.file || '<id>.rego'`（`server.js:170-172`），改已有规则写回它自己那份，不另起同 id 文件。
- 单测 `agent-api.test.js:607`：临时规则目录放两条规则 → 改一条后**另一条逐字节不变**、被改的那份等于新正文、整库仍是 2 条；
  再新增一条 → 目录里只多一个文件；模型给子集外语法（`input.host =~ "..."`）→ reject 且原文件不变、目录里没有 `.` 开头的临时文件；
  `ready:false` / 非法 id 也都不落盘。

### A3 wiki 维护者改的是方法论。两个维护者都不是分析的那个 Agent

- 规则维护者：模型 + `prompts/rule-maintenance.md`（`prompt-store.js:18` 注册），与 `InvestigationAgent` 两套东西。
- wiki 维护者：`WikiWorkbench` + `prompts/knowledge-maintenance.md`——走已有知识维护会话（`wikiAgent.create` 建反馈会话，
  一轮 `wikiAgent.reply` 产出方法论修订），再用 `wiki.publishBundle` 的发布前检查（编号、frontmatter、证据引用、断链）
  把页面**真的写进去**（`server.js:228-248`）；只出草案、页没写上 → `failed`。
- 单测 `agent-api.test.js:649`：把研判器换成「一被调用就抛 `误报维护不该重新跑研判`」的替身，POST 完等维护收尾，
  断言 `run()` 一次没被调；规则维护者拿到的材料是案件自己的 `msgid`/`payload` 与 `rule_ids`（来自 `result.json`），
  wiki 维护者拿到的 `expected_verdict === 'false_positive'`、目标页是分析时引用过的 `honeypot/HP-10.md`，
  `publishBundle` 的 `reviewer` 是登记人、`note` 是他给的理由。

### A4 维护失败不把这一条的误报结论改回去，并能看出更新中、已更新或失败

- 单边失败只写自己那一格（`server.js:211-219`）：`maintenance.rule` / `maintenance.wiki` 各自 `{status, at, error?}`，
  `verdict` 与 `feedback` 一个字都不动；总态 `maintenanceState`（`server.js:106-109`）：还有一边在跑 → `updating`；
  都收尾后任一边失败 → `failed`；否则 `updated`。状态随记录 `persist()`，`GET /api/agent/triage/{alertId}` 读得到。
- 单测 `agent-api.test.js:693`：规则维护者抛「模型接口 HTTP 500: 上游不可用」、wiki 成功 → 等收尾后断言
  `record.verdict === 'false_positive'`、`verdict_label === '误报'`、`feedback.reason` 原样，`maintenance.status === 'failed'`、
  `rule.status === 'failed'` + `rule.error` 带原文、`wiki.status === 'updated'` + `wiki.revision`；GET 同一条也是这个结论。
- 单测 `agent-api.test.js:724`：记录上残留 `maintenance.status === 'updating'`（模拟重启前留下的）但不挡重新登记——
  重新 POST 会重起一轮并收尾到 `updated`/`failed`，结论仍误报。防重复登记靠 `runningMaintenance`（`server.js:459`、`:615`）。

## 五、未决

1. **研判重跑会把人工误报结论覆盖掉**：`triage-monitor.js:446` 在 `run()` 收尾无条件写 `record.verdict`。
   本卡只在 `done` 的记录上登记误报（未完成回 409），但重跑一条已登记误报的告警仍会改回 AI 结论。
   该文件不在本卡 scope，没有顺手改；要收口得单开一张卡（在 `run()` 收尾判断「人工结论优先」）。
2. **wiki 页是模型正文自动发布**：本卡裁决要求「必须真的改一页方法论」，所以维护者产出的正文直接走 `publishBundle` 写页，
   `reviewer` 记登记人、`note` 记他给的理由，审计链上是「值守分析员登记的误报触发的维护」，**不是人工逐字审阅过的正文**。
   发布前检查（编号、frontmatter、证据引用、断链）是拦得住的，语义质量没人看。若不能接受，下一步应加「人审确认」环节。
3. **维护没有断点恢复**：维护状态存在案件记录里，进程在 `updating` 时死掉，记录会一直显示 `updating`；
   重新登记能重起一轮（`runningMaintenance` 不拦），但没有自动恢复/超时标记，也没有「维护历史」。本卡只保证「不锁死」。
4. **规则维护者的产出只过了语法子集与 id 校验**，语义是否收紧得对、会不会把这一类攻击改宽，没有回放或人工审。
   `ready:false` 是唯一的质量闸门。
5. **`docs/architecture.md:201` 已过时**：那里写「`prompts/` 下有 6 个核心提示词文件」，现在 7 个（新增 `rule-maintenance.md`）。
   该文件不在本卡放开路径内，没动。
6. **`docs/modules/http-api.md` 其余锚点仍是旧基线**：文件头声明其余 `文件:行号` 指向 `server.js` 496 行版本（`commit 63f1379`），
   本卡只把新入口相关的锚点按当前 `server.js`（808 行）标号，并在文件头写明。全量锚点复位是单独一张卡的量（107 个锚点）。
7. **没有真模型/真 wiki 目录的端到端跑**：本机没有 `LLM_*` 配置，两个维护者的真实产出质量、`publishBundle` 对真实模型正文的
   通过率都没验；单测里模型、会话、发布全是替身。
