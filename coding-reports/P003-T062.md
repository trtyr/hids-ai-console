## 1. 审计事件模型（acceptance 第 1 条：设计先行）

**事件形状**：`{ at, actor: {kind, id}, action, object, before, after, result, request_id }`

| 字段 | 口径 |
|---|---|
| `actor` | `{kind, id}`：`user`（Basic 登录名；未鉴权部署如实标 `anonymous`，不留空）/ `token`（静态管理员令牌的**用途标注** `rule-admin`/`prompt-admin`，不含明文）/ `system`（后台动作 `backend`）。领域层硬校验：没有 actor 的事件构造不出来 |
| `action` | 24 个具名动作（`AUDIT_ACTIONS` 单一真源）：config.write / triage.enqueue / triage.control / triage.cancel / false-positive.register / investigation.run / trace.start / rule.write / rule.rollback / triage-rules.write / wiki.page.write / wiki.maintain / wiki.publish / data.cleanup / logs.cleanup / maintenance.login / maintenance.logout / maintenance.package.stage / maintenance.package.apply / case.dispose / case.assign / fp.session.write / rule.maintain（后三个供 T063/T088/T089 扩展用，已入表） |
| `object` | 被操作对象的最小标识（`{kind:'rule', id, rev}` / `{kind:'case', alert_id}` / `{kind:'config', keys, source}`…） |
| `before/after` | 配置类记新旧值；**机密键值一律 `[redacted-changed]`**（`redactValues()`）——「改过」可见，「原文」不可见 |
| `result` | `ok` / `denied`（令牌无效、登录失败）/ `error` |
| `request_id` | 从 T072 的 ALS 请求上下文自动取——审计与技术日志同链 |

**存储形态**：append-only JSONL 按天分文件 `<数据根>/audit/audit-<日期>.jsonl`（目录 0700 / 文件 0600）。**技术日志 vs 审计流的边界**：技术日志（logs/）可轮转、可被 `/api/logs/cleanup` 与 `/api/data/cleanup` 清理，是运维排障的流水；审计流独立在 `audit/` 目录，**不参与任何清理口径**（T061 的清理类型不含 audit），只增不改。查询（`GET /api/audit`）读的是审计文件，不是日志。

**防篡改程度**：append-only 写（appendFile）+ 独立目录；进程内无删除/改写入口。物理防篡改（WORM/校验链）属部署层职责，报告如实标注为边界（运维可用文件系统权限收紧 `audit/` 目录）。

**保留策略**：不轮转不清理，随数据根持久化；体量估算：每事件约 300–600 B，按日均 200 次写操作 ≈ 0.1 MB/日，一年 ≈ 40 MB——无容量风险。
