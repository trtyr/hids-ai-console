## 二、验收逐条

### A1 `GET /api/agent/triage/cases` 能按结论、类型、主机、时间筛，能按结论把 threat 排到前面，分页回 total

- 筛：`triage-monitor.js:118-124`（结论/类型/主机/时间四类），HTTP 解析与 400 在 `server.js:158-176`；时间筛与案件创建用同一个 `eventSeconds`（部署端偏移生效），含端点。
- 排序：`sort=verdict`，`triage-monitor.js:127` + 档位 `triage-monitor.js:8`；同档靠 `Array#sort` 稳定性保持时间倒序。
- 分页回 total：`triage-monitor.js:128` 的 `total` 是过滤后条数，切页在过滤之后。
- 证据（单测）：`node --test triage-monitor.test.js` → 8/8 绿；`node --test agent-api.test.js` → 7/7 绿。HTTP 侧断言含 `?verdict=threat` / `?type=webshell` / `?host=10.0.0.5` / `?from=&to=` / `?sort=verdict` / `?verdict=threat,uncertain&count=1&offset=1`（total 仍是 2）。
- 400 口径：`agent-api.test.js` 覆盖 `verdict=bogus`、`type=nonsense`、`sort=level`、`from=not-a-time`、`from` 晚于 `to`、`count=0` 六种，正文逐条断言。

### A2 用 syslog 形态的 alert_id 能打开这条研判，不要求先有牧云事件号

- 实现本来就在：`server.js:107-109` `validTriageId()` 接受 `syslog:<类型>:<指纹16位>:<秒|unknown>:<uuid>`，`triage-monitor.js:105-110` `status()` 先按 `alert_id` 精确找、再按 `matched_alert_id` 反查。**本卡没改这条链路的代码**，新增的是钉住它的用例（原实现无测试）。
- 证据：`agent-api.test.js` 新用例——记录 `matched_alert_id = null`（没匹配到牧云事件）仍能用 syslog ID GET 到 200（`status=done`、`repeat_count=2`、`input` 不外露）；`monitor.cases()` 列表项的 `alert_id` 原样能再打开（回环）；形状合法但没入队的 syslog ID 回 `not_queued` 占位而不是 404；形状不对才 400。
- 契约：`openapi.yaml` `TriageCaseListItem.alert_id` 描述写明「用它就能打开本条研判，不要求先有牧云事件号」。

### A3 重复次数沿用 repeat_count，不另造计数

- 列表项只有 `repeat_count`（`triage-monitor.js:133`，缺省 1），没有 `occurrence_count` / `delivery_count` 之类的第二份计数；写入侧的累加仍在原来的同秒折叠分支（`triage-monitor.js:264` 附近，未改）。
- 证据：`triage-monitor.test.js`「列表的重复次数沿用例记录上的 repeat_count，不另造计数」——断言 `repeat_count=3` / `=2` 原样出现在列表项，且每个列表项都没有 `occurrence_count` / `delivery_count` 键，记录上缺 `repeat_count` 时落 1 不是 0。
- 契约：`openapi.yaml` `TriageCaseListItem.repeat_count` 写明「直接沿用记录上的 repeat_count，本列表不另造计数」。
