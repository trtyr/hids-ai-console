## 二、验收逐条

### A1 有结论分布、类型分布、从某个时刻起的计数

- 结论分布：`triage-monitor.js:168` 初始化四键（空队列也给零值，不给 `undefined`），`triage-monitor.js:173` 累加；口径与 `cases({verdicts})` 一致——没有结论算 `review`。
- 类型分布：`triage-monitor.js:174-175`，键取自 `eventTypeFor(msgid)`（`syslog-input.js:59`）同一张映射表；没有 `input` 的记录（轮询入口入队）或 MsgId 不在表里，计入 `unknown`。
- 从某个时刻起的计数：`summary({ since })`——`since` 归一成 RFC3339 回显，三个聚合（`counts` / `verdict_counts` / `type_counts`）共用同一份过滤后的记录集（过滤行 `triage-monitor.js:171`），比较对象是记录的 `created_at`（进入队列时刻），**含端点**；HTTP 侧参数解析在 `server.js:284-291`。
- 证据（单测）：`triage-monitor.test.js`「summary() 出结论分布、类型分布，since 只算该时刻起进入队列的记录」——6 条最小记录矩阵断言三组分布；`since` 之后只剩 4 条（`done 2 / queued 1 / failed 1`）；正好落在 `since` 上的记录也计入；未来时刻全零但键在；`since` 解析不出来退回不带筛且回显 null；缺 `created_at` 的旧记录不带筛照常计、带筛被排除。`agent-api.test.js` 覆盖 HTTP 层同一矩阵 + `?since=2026-11-04T00:00:00Z`、秒级时间戳、`?since=not-a-time` → 400「筛选起始时间无效：not-a-time」、`?since=`（空）→ 200 且 `since:null`。

### A2 summary 在 syslog 模式下给出最后一条什么时候到的，不再只有永远为空的 last_poll_at

- `triage-monitor.js:180-181`：syslog 模式的 summary 带 `last_received_at`（ISO，到达时刻）；`last_poll_at` 保留（syslog 模式本来就恒 null，前端仍能读到这个键），两个键互不替代。
- 写入点只有两处真实入队：新报文 `triage-monitor.js:315`、同秒折叠 `triage-monitor.js:295-299`。**解析失败 / MsgId 无对应场景 / 暂停期间被跳过**都不推进这个值——「最后一条什么时候到的」只算真正进了队列的报文。
- 持久化：`persist()` 写 `last_received_at`，`load()` 恢复（`triage-monitor.js:67` / `triage-monitor.js:88`），重启后退回 null 才算丢。
- 证据（单测）：`triage-monitor.test.js`「syslog 模式的 summary 给出最后一条到达时刻，重启后不丢，失败投递不算」——用 `t.mock.timers` 钉死时钟：一条没收到是 null、绑上 UDP 端口后仍是 null、首条报文的时刻精确等于 `2026-11-03T08:00:00.000Z`、`tick(7000)` 后折叠重复投递推进到 `08:00:07`、时钟再往前走时解析失败与未知 MsgId 都不推进、暂停期间 `{skipped:'paused'}` 不推进、重启后 `load()` 仍是 `08:00:07`；poll 模式 summary 没有 `last_received_at` 键（有 `interval_ms`）。
- `agent-api.test.js` 覆盖 HTTP 层：syslog 模式响应里 `last_received_at` 原样透出、`last_poll_at` 为 null；poll 模式响应里没有这个键。
- 契约：`openapi.yaml` `TriageSummary.last_received_at` 写明「到达接收服务器的时刻（接收端时钟），重启后不丢；解析失败 / 未知 MsgId / 暂停跳过不算收到」，`last_poll_at` 写明 syslog 模式恒 null 且指向新字段。

## 四、未决

1. **`docs/modules/triage-pipeline.md:470` 的 `summary()` 字段表变旧**——那张表现在只列到 `counts` + `last_poll_at` + `syslog`，没有 `verdict_counts` / `type_counts` / `since` / `last_received_at`。本卡 scope 没给 `docs/**`（只有 `openapi.yaml`），所以只把契约写进 OpenAPI，**没动那份文档**。需要一张后续卡把 §5.4 / §8 的字段表补齐，否则读文档的人看不到新字段。
2. **`web/README.md:245` / `web/README.md:306` 的队列汇总字段清单也旧了**——`web/**` 是本卡 forbidden，未动。总览页要展示分布属于前端那条线的事。
3. **结论口径的历史值**：`verdict_counts` 把不属于三态的值（历史快照里的 `undetermined` / `needs_review`）计入 `review`。正常链路不会出现——`investigation-agent.js:13` 的 `verdictMap` 已把非三态归一成 `uncertain`；但 `cases({verdicts:['review']})` 对这类值是不匹配任何筛选（`triage-monitor.js:118` 用 `record.verdict || 'review'`），两个接口的历史值口径不完全一致。本次没动 `cases()` 的既有口径（不在验收范围，改了会动别人的测试）。
4. **`since` 比的是入队时刻而不是牧云事件时间**——和 `cases` 的 `from/to`（比 `event_time`）是两个口径。总览问的是「队列里这段时间进来多少」，所以用 `created_at`；文档已在 `openapi.yaml` 写死。若产品口径要的是事件时间，需要改（属改需求，不属改 bug）。
5. **没有 `created_at` 的旧记录在带 `since` 时不计数**（没有时刻可比，`Date.parse(undefined)` 是 NaN）。已在 `openapi.yaml` 写明；要不要给这类记录兜底（例如按 `updated_at` 退）需要产品定。
