# P003-T089 交付报告 · 四 Agent 共性

**落地**：
1. **统一进度推送** ✅：`GET /api/events?topics=triage,board,investigation,fp&interval_ms=2000`——一条 SSE 连接承载四类进度。事件格式统一为 `{type: snapshot|progress|error, topic, at, ...}`；订阅即推一次快照，之后按指纹变化推 progress，15 秒心跳。与既有 `/api/agent/investigations?stream=1`（一次请求一路流）并存，不替代它。
2. **统一重试与降级** ✅：`recordFailure()`（shared/redaction）已是四域共用的失败归一；重试分类在 `triage-monitor.scheduleRetry`（指数退避 + 死信上限）、`investigation-agent`（超时重试一次）、`wiki-workbench`/`fp-maintainer`（失败落会话 + 单腿补跑）。三处语义一致：**可重试＝超时/上游瞬时；不可重试＝校验失败；需人工＝死信/连续失败**。
3. **三种会话的存储形状** ✅：FpSession / RuleSession / WikiSession 的 JSON 已刻意对齐（id/case_id/status/turns/messages/decision/validation/created_at/updated_at），批 5 迁移后三者在同一 maintenance 上下文；`WikiSession` 的 publish 状态机单独保留（forbidden 要求）。

**未做并说明**：
- **把三种会话合并成一个存储类**：三者语义不同（Fp 有幂等键与双腿、Rule 有 revision、Wiki 有 publish 状态机），合并会得到一个带 `if (type === ...)` 的万能类。裁决：**统一形状、不统一实现**——这正是卡面 forbidden「不合并三种会话的业务语义，只统一形状与生命周期」的字面要求。
- **四个 Agent 共用一份重试实现**：三处退避逻辑的触发条件不同（队列重排 vs 单次调用 vs 会话补跑），抽出共同抽象会引入与 T085/T086 相同的问题（把内部接线变成契约）。裁决：语义统一、实现各自（已在上面第 2 条列出对照）。
