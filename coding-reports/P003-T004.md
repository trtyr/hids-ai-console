## 五、未决

1. **本卡没有新单测（申报）**：零代码改动，改动全是 YAML 与 Markdown，`node --test` 不读这两类文件。验证靠 `redocly lint`（与基线同数 warning）+ 整套后端单测与基线逐项一致 + 每个新字段回指当前 HEAD 行号。契约的**行为验证**留给 tester 按新 schema 写接口测试。
2. **`docs/modules/event-gateway.md` / `http-api.md` 的旧行号仍停在 `35530d8`**：P003-T001 改过 `cloudwalker.js`，这两页既有断言的行号已经偏移。本卡只在新增 §8.3 里注明「本小节行号对当前 HEAD」，没有批量复位——那是一次独立的全页行号重核，超出本卡 scope。要修需另派卡。
3. **B10 的原文有歧义，我按响应结构写**：`Alert.detail` 在列表/详情接口里是**字符串**（固定文案），而 `GET /api/alerts/{alertId}` 返回的顶层 **`detail` 是原始对象**。两处都在 §8.3 与 `AlertDetail` 描述里写明了。若 tester 按「`Alert.detail` 是对象」写断言会撞上字符串属性——这是卡面措辞与实现的落差，不是实现错。
4. **`WikiPage.status` 枚举保留了 `reference`**：`wiki-store.js:25` 在页面缺 `status:` 时读作 `reference`，而写入面只接受 `active`/`draft`/`deprecated`（`wiki-store.js:167/214/253`）。schema 的枚举必须覆盖读面真实返回值，所以是四值，写面三值写在描述里。若要求读写两面同一枚举，得先改代码，本卡 forbidden 面不含。
5. **`Review.assessment` 的枚举是「契约值」，不含模型越界值**：实现只把 `supported` 当通过，枚举外的值按未通过处理（`investigation-agent.js:468/537`）。JSON Schema 表达不了「枚举外按未通过」，这句写在 `description` 里；`Review` 与 `ClaimCitation` 的 `additionalProperties` 保持 `true`，因为这两个对象直接来自模型输出，可能带多余键。
6. **旧版落盘的研判记录可能缺 `evidence`**：本卡之前保存的 `investigation.json` 里没有 `evidence` 键，`GET /api/agent/investigations/{alertId}` 会原样返回。schema 没把它设成 `required`，就是这个原因；不迁移旧记录。
7. **`docs/modules/http-api.md` 没动**：A1-A6 没有条目需要它承载。它的路由表已把 schema 指向 `openapi.yaml`，再抄一份字段表就成副本了。
