# P003-T053 recon — syslog-pipeline.test.js:96 抖动修复

结论先行：**实现侧没有 bug，是测试侧漏了文档写明的「等落盘」同步点**——测试在内存态看到 `done` 后立刻用新实例 `load()` 读磁盘快照，
而快照由 `run()` 收尾的合并写异步落盘，读到的可能是「第三条记录入队之前」的那一版快照。

## 1. 功能理解

`npm test` 主门偶发假红：`syslog-pipeline.test.js` 的「syslog 逐条研判保留材料、三态结果…」用例约 1/8 概率在
`assert.equal(resumed.cases().total, 2)`（`syslog-pipeline.test.js:96`）失败，actual 1 / expected 2。
要把它变成确定性：负载下连跑 ≥30 次 0 假红，且**不许删断言换稳定**（删了断言要能被同文件其他断言或守卫抓住）。

## 2. 复现（原树，bea34bd，未改一行前）

- 静默基线：单跑该文件 12 次、并发 8×5 轮跑该文件 40 次 → 全绿（窗口太窄，单文件压不出来）。
- 主门复现：`npm test` 连跑 60 次 → **1 次假红**（第 43 次），落点 `syslog-pipeline.test.js:96:10`，`actual: 1 / expected: 2`
  （另一次 30 次连跑在第 29 次同样命中，两轮独立复现，概率与卡面「约 1/8」同量级——实测约 1/30~1/45，见报告）。
- 失败面：`resumed.cases().total` = 1，即 `load()` 读到的快照里**只有第一条记录**（第三条尚未进快照）。

## 3. 根因（调用链，精确到行）

| 环节 | 位置 | 事实 |
| --- | --- | --- |
| 第三条记录入队 | `triage-monitor.js:870-894` | 只 `markDirty()`（:894），不 await 落盘——合并写是 A4 的设计 |
| 研判跑完 | `triage-monitor.js:1045` | `record.status = 'done'` 先改**内存**记录 |
| 收尾落盘 | `triage-monitor.js:1072-1079` | `markDirty()` + 队列空时 `await this.flush()`——这一步在 `status='done'` 之后才发生 |
| 测试观察 `done` | `syslog-pipeline.test.js:88-91` | 轮询 `monitor.status(...)`，看的是**内存**态 |
| 测试读磁盘 | `syslog-pipeline.test.js:94-95` → `triage-monitor.js:177` | 新实例 `load()` 直接 `readFile(this.file)`，没有任何等落盘的屏障 |

于是：轮询 5ms 一次看到 `done` 的时刻，`run()` 的 `flush()`（mkdir → writeFile → rename 三次异步 I/O）可能还没 rename 完，
`load()` 读到的是上一条 `await this.persist()`（跨秒复用路径 `triage-monitor.js` reused 分支）写下的快照——那版快照里还没有第三条记录。
主门并发 27 个测试文件时 I/O 排队，窗口从亚毫秒涨到毫秒级 → 偶发假红。

**文档口径**（docs-first）：`docs/modules/triage-pipeline.md:360` / `:829` 明写
「`writeChain`（getter）｜测试与调用方当「等落盘」的同步点｜等价于 `persist()`（`triage-monitor.js:246`）」；
`:1016` 写「队列闲下来时收尾立刻落一次」。所以实现行为与文档一致，缺的是测试侧那次 `await`。
