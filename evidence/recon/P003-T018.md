## 一、功能理解

误报入口（`POST /api/agent/triage/{alertId}/false-positive`，P003-T013）把结论写进研判记录后，这条记录还能被
`POST /api/agent/triage/{alertId}`（`retry:true`）重新排队重跑。重跑收尾时 `TriageMonitor.run()` 无条件把
AI 那次的 `verdict` / `verdict_label` / `summary` 盖回记录（`triage-monitor.js:443-447`），于是人工登记的误报结论被抹掉；
更要命的是 `enqueue()` 重排时整条记录被换掉（`triage-monitor.js:215-220`），连 `verdict` / `feedback` 都不留在记录上。
本卡：已标误报的记录，重跑写回不得覆盖结论三件（A1）；没标误报的记录行为照旧（A2）；误报入口本身（`server.js`）一个字不动（A3）。

## 三、依赖影响面

- **重跑只有一条路径**：`POST /api/agent/triage/{alertId}`（`server.js:640`）→ `enqueue(alertId, { retry: true })`。
  `poll()` 对已有记录不再入队（`triage-monitor.js:254`），`_acceptSyslog()` 同指纹同秒只累加计数（`triage-monitor.js:294-311`），
  不同秒是新 `alertId`，都不会重跑旧记录。所以修 `enqueue` + `run` 两处即覆盖全部重跑。
- **谁读这些字段**：`status()`（`triage-monitor.js:110-116`，去掉 `input` 后摊平记录）、`cases()`（`:133-147`，列表的
  `verdict` / `verdict_label` / `summary` / `decision_source` 列）、`summary()` 的 `verdict_counts`、`contextFor()` 的
  `history[].conclusion`；HTTP 侧 `GET /api/agent/triage/{alertId}` 与误报入口的 `falsePositiveView`（`server.js`）都从记录上读。
  保留 `decision_source='human'` 才能让列表与详情的「来源」列继续显示人工。
- **连带要跑的测试**：`triage-monitor.test.js`（本卡主战场）、`agent-api.test.js`（误报入口 4 条用例：`enqueue` 带字段后
  不能改变「`status !== 'done'` 拒绝登记」与重复登记口径）、`integration.test.js`、`syslog-pipeline.test.js`。
- **持久化**：保留的 `feedback` / 结论字段会随 `persist()`（`:87-98`）落进 `queue.json`，重载后仍在（`load()` 只改 `running → queued`）。
