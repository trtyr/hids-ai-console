## 一、功能理解

值守分析员把一条已完成研判判成误报时，要有个入口写下结论和理由：**这条结论立刻生效**（不等谁来维护）。
随后两个维护者各自去改自己的东西——规则维护者改 Rego（只加一条或改一条，不重写整本），wiki 维护者改方法论页；
两个维护者都不是跑研判的那个 `InvestigationAgent`。任意一方维护失败只写进维护状态（更新中 / 已更新 / 失败），
**不把已经落盘的误报结论改回去**。

## 三、依赖影响面

- **写入落点只有两处**：`monitor.records` 上那条案件记录（`verdict` / `verdict_label` / `decision_source` /
  `feedback` / `maintenance` / `detail` / `updated_at`），以及 `rules/<id>.rego` 这一份文件。
  两者都不改别的模块：`triage-monitor.js`、`rule-store.js`、`wiki-workbench.js`、`wiki-store.js` 一字不动。
- **谁在读这些字段**：`GET /api/agent/triage/{alertId}`（`monitor.status()` 摊平记录）、
  `GET /api/agent/triage/cases`（列表项里 `verdict` / `verdict_label` / `decision_source`）、
  告警列表与详情里内嵌的 `triage`。列表不摊 `maintenance`/`feedback`，只影响结论与来源两列。
- **研判重跑会覆盖人工结论**：`triage-monitor.js:446` 在 `run()` 收尾时无条件写 `record.verdict`。
  本卡不改它（scope 外）；误报入口因此只接受 `status === 'done'` 的记录，且不改已落盘的历史研判记录。
  重跑覆盖仍是已知风险，记进报告「未决」。
- **`rules/` 目录被分析链路读**：`investigation-agent.js` 每条 syslog 研判都会 `ruleStore.evaluate`，
  一个坏规则文件会让研判求值报错。所以写入前必须在临时目录里用**真的 `RuleStore`** 解析校验，
  写入后再 `list()` 确认整库仍可装载；写入用临时文件 + `rename`，不留半截文件。
- **wiki 页被分析链路读**：`WikiStore` 页面改动影响下一次研判的判据。wiki 维护者必须走
  `wiki.publishBundle`（自带 `checkBundle`：编号、frontmatter、证据引用、引用不存在判据都拦），不能用裸写。
- **受影响的既有测试**：`agent-api.test.js`（新增用例）、`wiki.test.js` / `rule-store.test.js`（只读校验，不改）、
  `update-store.test.js`（`snapshot.sections` 多一个 `rule` 键，用例自造 payload，不受影响）。
- **`/api/agent/prompts` 多一节**：`prompt-store.metadata()` 会列出 `id: 'rule'` 的核心提示词，
  `docs/architecture.md:201` 那句「6 个核心提示词文件」由此过时——该文件不在本卡放开路径内，记进「未决」。
