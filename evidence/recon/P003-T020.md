# P003-T020 侦查记录：规则维护者不得放宽原条件

## 1. 功能理解

现场测试（`docs/_meta/live-test-2026-11-19.md`，主仓未提交文档）里，误报登记触发的规则维护把
`rules/webshell_drop.rego` 的 `startswith(input.path, "/tmp/")` 改成了 `startswith(input.path, "/tmp")`，
同时加了 `not contains(input.path, "hids-live-test")`。前者是**放宽**：`/tmp/a.jsp` 之外，
`/tmpfoo/a.jsp`、`/tmpabc.jsp` 这类路径也开始命中；换句话说，原本不命中的真后门现在可能命中——而放宽的代价
在误报方向上表现为「把真攻击也一起放进来」，但这条路径的实际危害是**把一次现场测试的排除写进了生产规则**
（后缀多一个斜杠的差异），且 `hids-live-test` 排除会让文件名带这个串的真后门静默漏报。

这一卡要做三件事：

1. **维护者改已有规则时，原有条件必须还在、且不许更宽**——校验不过就不落盘，维护判 `failed`（A1/A3）。
2. `rules/webshell_drop.rego` 回到原版：无 `hids-live-test` 排除、前缀 `/tmp/`（A2）。
3. 上一条已经落盘的那份，在报告里写明白（A3 后半句）。

## 3. 依赖影响面

- **调用方**：`maintainFalsePositive`（`server.js:209` 附近）只把 `maintain()` 的异常记进 `maintenance.rule.error`（截 300 字）并判 `failed`，不碰 `verdict`。所以新增的拒绝路径天然满足「维护失败只写 maintenance」。
- **表达式形状**：`rule-store.js:51-63` `parseExpression` 只认 `input.<字段> (==|!=) <字面量>` 与 `(contains|startswith|endswith)(input.<字段>, <字面量>)`，可带 `not`。`rule-store.js:107-113` `holds()` 给出求值语义（缺字段时引用它的表达式不成立）。**本卡不改 `rule-store.js`**（在 scope 外，且已被 P003-T011 钉住）；`server.js` 侧只做抽取与比对。
- **既有测试要看住**：`evidence/test/P003-T013/acceptance.test.js:37-51` 的 `HONEYPOT_UPDATED` 是「保留四条原条件 + 新增一条 `input.source_ip != "203.0.113.9"`」——属于收紧，新检查必须放行它，否则 T013 的规则维护用例会红。同文件的 `BAD_SUBSET_REGO` 走的是 `validateRego`（子集外语法），在新检查之前就失败，不受影响。
- **回归面**：`node --test *.test.js evidence/test/P003-T013/acceptance.test.js` 基线 = 199 条 / 197 过 / 1 挂（`maintenance-startup.test.js` 的 symlink 用例，子进程 `MODULE_NOT_FOUND`，与本卡无关，改动前就挂）/ 0.83s。`web/**` 的用例在本树缺前端依赖，全挂——禁改，不在本卡范围。
- **文档**：`docs/modules/http-api.md:161-166` 是规则维护的权威段（两道校验、`updated` 含义），`docs/modules/triage-rules.md` 是规则子集说明（无放宽口径，不需改）。
