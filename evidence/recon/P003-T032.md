## 三、依赖影响面

- **产品代码零改动**：本卡所有改动都在 `evidence/` 与 `coding-reports/`、`docs/_meta/`，`npm test` 基线（198 条）不受影响；收尾前重跑一遍只为确认没被环境副作用污染。
- **探针会写运行态**：`server.js:997-1010` 的 `runtimePaths()` 把运行态钉在**本仓 `.data/`**（本树起活时没有 `.data/`）。探针起真进程会造 `.data/triage-monitor.json`、`.data/trace-boards/`、`.data/investigations/`——`.gitignore:10` 已忽略，探针收尾自己清掉自己造的那几个。
- **端口**：所有替身与探针端口都用 0 动态分配，不占 8080/18081/15514，不撞正在跑的实例。
- **30s 轮询上界**：`TriageMonitor` 的 `intervalMs` 缺省 30000（`triage-monitor.js:36`），`server.js:51-56` 没注入更小的值——A2 探针必须等一个轮询周期（~31s×2），这是产品行为不是探针的毛病。
- **A2 恢复语义**：`setEnabled(true)` 把游标重置为点击那一刻的秒，并把 `queued` 记录逐条删掉——**暂停期间到达的告警恢复后不补跑**（`triage-monitor.js:199-207`，文档 `docs/modules/triage-pipeline.md` §5 `R-TRIAGE-06` 同口径）。所以 A2 的「续跑」只能验「恢复后新到的告警入队并跑完」，不能验「补跑暂停期的积压」。
- **A3 建边需要的最小替身面**：`TraceBoardService.start()` 先 `get_<type>_event`（走 `/rpc`）起板，`investigate()` 按资产节点调 `list_host_assets` → `list_host_events` → `list_global_events`（走 `/api/mcp`），模型两个动作（`investigate` → `conclude`）。MCP 的 `initialize` 必须回 `serverInfo.name='cloudwalker'` 且 `capabilities.tools`（`mcp-client.js:41-48`）。
- **A2 跑到 `done` 需要的最小模型面**：一轮 `wiki_page`/`wiki_search` 工具调用（否则结论被判「没查知识库」退回，`investigation-agent.js:159`）→ `submit_conclusion`（verdict 存疑 + summary + wiki_reason）→ 独立复核那次 `content` JSON（`assessment:'supported'`）。
- **A5 依赖**：卡面写「依赖 T035 已合并」。实测 `git rev-parse task/hids-ai-console-P003-T035` == `44eca4b`（= main），该分支零提交；群名册里 P003-T035 的席位正在跑。**依赖不成立**。
