# SC-14 · 重复：先分清「重复投递」和「重复行为」

**这两个词长得一样，含义完全相反。**

| | 重复投递 | 重复行为 |
| --- | --- | --- |
| 是什么 | 同一条告警被推送了 N 次 | 同一条命令真的被执行了 N 次 |
| 判据 | **同一秒** + 内容指纹相同 | 同一内容指纹，**不同秒** |
| 是什么性质 | **噪音** —— 传输层的问题 | **证据** —— 行为层的特征 |
| 怎么处理 | 折叠成一条，次数保留，**不重复判定** | 每次都判定，次数进事实层 |

**为什么必须分开**：重复投递会让「同一会话里发生了 8 次不同的操作」变成假象 ——
事实层的 `same_session_event_count` 会被灌成 8，判定链直接被带偏。
而重复行为是真信号，抹掉它等于把证据扔了。

## 次数是证据，不是结论

**反直觉但重要：次数多，不必然是威胁。**

合法软件反复跑（健康检查、监控探针、日志轮转）也会这样。
反过来，**只发生一两次的反而更可疑** —— 攻击者不会在同一台机器上重复操作几十次来留痕。

所以：**不要把「次数 > N」写成本类的判据。** 次数只是判据的**一个输入**。

## 怎么用这个数

| 情况 | 怎么判 |
| --- | --- |
| 反复执行 + 命令类型本身是硬证据（矿工 / 反弹 shell / SUID 提权） | **加强**真实威胁。自动化攻击不会只做一次 |
| 反复执行 + 路径已登记 + 执行者身份清楚 | **仍然是误报**。重复不改变豁免 —— 豁免的是「这一条命令」，不是「这个命令跑了几次」 |
| 反复执行 + 执行者身份不明 / 路径可疑 | **加强**存疑 → 倾向真实威胁 |
| 反复执行 + 命令本身无害（`ls` / `grep` / `find`） | **不加强**。重复跑无害命令不说明什么 |

## 事实层给的三个数（不要自己数）

| 字段 | 含义 |
| --- | --- |
| `same_session_event_count` | 窗口里**不同事件**的条数（重复投递已在上游折叠） |
| `same_session_occurrence_count` | 窗口里这些事件的**总出现次数** |
| `same_cmdline_repeat_counts` | 每条命令各出现几次 |
| `current_repeat_count` | 当前这条被推了几次（1 = 没有重复投递） |

⚠️ **这几个数是事实层算好的，直接用。** 自己数一遍会数错，
而「差不多对」在判定链里就是抖动（D-15）。

## ⚠️ 次数分两种，别混

| | 含义 |
| --- | --- |
| **投递次数** | 这条告警被推了几次（同秒重复） |
| **执行次数** | 这个命令真的跑了几次（跨秒重复） |

**同秒的重复投递不增加执行次数** —— 命令没多跑一次。
上游会把这两个数分开记，事实层给的是**执行次数**。

## 折叠不等于丢弃

重复投递被折叠后，**次数必须留在结论里**（`repeat_count`）。
运维看到「这一条出现了 8 次」是有用的信息，而且这个次数本身也是证据。
