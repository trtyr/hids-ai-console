# 硬证据与弱信号

## 为什么必须分

模型最常犯的错，是**把弱信号当硬证据用**：

- 「来源 IP 不认识」→ 判真实威胁
- 「时段在凌晨」→ 判可疑
- 「看起来像后门」→ 判真实威胁

**这些都不够。** 来源不认识可能只是运维在出差；凌晨可能是被叫起来修故障。

## 什么叫硬证据

**能单独定罪的，才叫硬证据。**

| 类 | 硬证据 |
| --- | --- |
| WebShell | ① web 目录 + web 进程写的 + 技术栈对 ② 被访问时外连过 ③ **代码本身就是后门形态**（混淆 + 解码链 + 外部输入到执行） |
| 异常登录 | 不可能旅行（1 小时内跨洲）；登录后 5 分钟内出现提权/可疑命令 |
| 可疑命令 | 反弹 shell 完整形态；给**系统自带**命令加 SUID；提权链秒级相连 |
| 蜜罐 | 深度交互 + 同主机紧跟攻击行为 |

## 弱信号只能加权

| 弱信号 | 为什么不能单独用 |
| --- | --- |
| 来源 IP 陌生 | 运维会出差、会连客户网络 |
| 时段异常 | 半夜故障要处理 |
| 频次低 | 「第一次见」不等于恶意 |
| 归属地漂移 | 可能挂着 VPN |
| 代码里有 `eval` | 正常业务代码到处都是 |

**弱信号的正确用法**：几条同向时**提高置信度**，但不能单独翻转结论。

## 一条容易搞错的

**硬证据不看「谁写的」。**

WebShell 的第三条硬证据（代码本身就是后门）**故意不要求 owner 是 web 进程**——
因为「攻击者提权后以 root 在 web 目录写了个后门」是最典型的形态。
只看 owner 会把这种案子判成存疑。

> **代码摆在那里，是后门就是后门，跟谁写的无关。**
